1. Introduction: Why This Project Exists

Super Mart is a small online grocery store. A visitor can browse categories like Fruits, Dairy, or Meats; see featured and clearance items on the home page; add products to a cart; register and log in; and an administrator can upload a spreadsheet full of products to populate the catalogue.

But the real point of the project is not the groceries. It is to understand MVC architecture — the way most modern web frameworks organise code so that the data, the user interface, and the logic that connects them stay cleanly separated.

This document explains the entire journey, starting from the absolute basics of how a web application even works, through the ideas behind MVC and Laravel, and into the concrete code of Super Mart. If you read it in order, you will understand not just what each file does, but why it exists at all.

2. How the Web Works: Client, Server, and Database

Before talking about MVC, we need to understand the three machines that participate in almost every web application.

2.1 The client (the browser)

The client is the program the user runs — Chrome, Firefox, Safari. It renders HTML, runs JavaScript, and sends requests to a server. When you type a URL or click a link, the browser sends an HTTP request.

HTTP is a simple text protocol. A request looks roughly like this:

GET /category/meats HTTP/1.1
Host: supermart.test
Accept: text/html

The first word (GET) is the method — what kind of action you want. The most common are:

  • GET — "give me a page."
  • POST — "here is some data, save it" (a form submission).
  • DELETE — "remove this thing."
  • PUT/PATCH — "update this thing."

2.2 The server (the application)

The server is a program running on another machine that listens for these requests and produces responses. In our case the server is a PHP application powered by Laravel. Its job is:

  1. Receive the request.
  2. Figure out what the user wants.
  3. Talk to the database if needed.
  4. Assemble an HTML response.
  5. Send it back.

A response looks like:

HTTP/1.1 200 OK
Content-Type: text/html

<!DOCTYPE html>
<html>... (the page) ...</html>

2.3 The database (the memory)

The database is where permanent data lives. The server forgets everything between requests, so anything that must survive — users, products, orders — is stored in a database. Super Mart uses SQLite, a lightweight database stored as a single file (database/supermart.sqlite). The data is organised into tables (like spreadsheets): a users table, a categories table, an items table.

┌─────────┐ 1. HTTP request ┌─────────┐ 3. SQL query ┌──────────┐ │ Client │ ──────────────────▶ │ Server │ ─────────────▶ │ Database │ │ Browser │ │ (Laravel│ │ (SQLite) │ └─────────┘ 4. HTTP response └─────────┘ 2. rows back └──────────┘ ◀────────────────────────── ◀───────────────

So a web app is a conversation: the browser asks, the server thinks and asks the database, the database answers, the server builds a page, and the browser shows it. Everything else in this document is about how the server is organised to do this cleanly.

3. What Is MVC Architecture?

MVC stands for Model–View–Controller. It is a way of splitting the code of an application into three distinct responsibilities so that each part has one job. The idea is decades old and underlies most frameworks you will meet (Laravel, Rails, Django, ASP.NET MVC, Spring).

3.1 The three parts

PartJobRule of thumb
ModelRepresents the data and the rules around it: what a User is, what an Item is, how they relate.Knows about the database. Does not know about HTML.
ViewRenders the user interface. Produces the HTML the browser receives.Knows about HTML. Does not know about the database.
ControllerReceives the request, asks the Model for data, hands that data to the View.The coordinator. Should stay thin — no heavy logic here.

3.2 The flow

Request │ ▼ ┌────────────┐ │ Controller │ ──asks──▶ ┌────────┐ │ │ │ Model │ ──reads──▶ Database │ │ ◀──data──── └────────┘ │ │ │ │ ──gives data──▶ ┌──────┐ │ │ │ View │ ──produces──▶ HTML │ │ ◀──HTML───────────└──────┘ └────────────┘ │ ▼ Response (HTML)

3.3 Why separate them?

If you mix everything together — database queries inside HTML, business logic inside templates — the code becomes impossible to change. Separation gives you three gifts:

  • Clarity: to find where a rule lives, you follow the layer. Data rule? Model. Markup? View. Request handling? Controller.
  • Reuse: the same Model can feed a web page, an API, or a CLI command.
  • Testability: you can test a Model without a browser, and a Controller without a database.
The one-sentence version: the Model knows the data, the View knows the screen, the Controller knows the user — and none of them knows more than it should.

4. Meet Laravel: A Framework That Speaks MVC

Laravel is a PHP web framework. PHP is the programming language; Laravel is the structure and the helpers. It is an MVC framework, meaning it gives you ready-made places for each layer:

  • app/Models/ — your Model classes.
  • app/Http/Controllers/ — your Controller classes.
  • resources/views/ — your View templates (written in Blade).
  • routes/ — the files that map URLs to controller methods.

4.1 Eloquent: the Model engine

Laravel's ORM (Object-Relational Mapper) is called Eloquent. An ORM lets you work with database rows as if they were objects. Instead of writing raw SQL like SELECT * FROM items WHERE id = 5, you write:

$item = Item::find(5);
echo $item->name;

Each model class maps to a table. The Item model maps to the items table (plural). Eloquent figures that out by convention.

4.2 Blade: the View engine

Blade is Laravel's templating language. It is HTML with extra directives. {{ $variable }} prints a value (safely, escaped). @if, @foreach, @csrf are Blade directives that compile to PHP. The View never talks to the database; it only uses variables the Controller handed it.

4.3 Artisan: the command-line tool

Artisan is Laravel's CLI (php artisan ...). It runs migrations, starts the dev server, lists routes, and more. You will see it throughout.

4.4 Composer and NPM

Composer is PHP's package manager — it installs Laravel and third-party libraries (like the Excel importer) into vendor/. NPM handles JavaScript and CSS assets, bundled by Vite into public/.

5. Designing Super Mart: The Domain

Before writing code, we list what the app needs to model. A supermarket has:

  • Categories — Fruits, Dairy, Meats, etc. Each has a name, a slug (a URL-friendly version), an icon, and a hero image.
  • Items (products) — each belongs to a category, has a name, slug, description, image, price, optional sale price, currency, and two flags: is_featured and is_clearance.
  • Users — visitors who register and log in.
  • A cart — a temporary collection of items a user wants to buy.

The relationships are simple: a Category has many Items; an Item belongs to a Category. A User is mostly independent for now.

6. Setting Up the Project

A Laravel project is created with composer create-project laravel/laravel super-mart. That gives you the skeleton: the app/, routes/, resources/, database/, and config/ folders, plus composer.json (PHP dependencies) and package.json (JS dependencies).

The .env file holds configuration that changes per environment — most importantly the database:

DB_CONNECTION=sqlite
DB_DATABASE=C:\Users\...\super-mart\database\supermart.sqlite

Setup is automated by a Composer script:

composer setup   # installs deps, copies .env, generates key, migrates, builds assets

For development, composer dev runs the server, queue, log tail, and Vite all at once.

7. The Model Layer: Data and Relationships

Models live in app/Models/. Three matter to us: Category, Item, User.

7.1 The Item model

class Item extends Model
{
    protected $fillable = [
        'category_id', 'name', 'slug', 'description', 'image',
        'price', 'sale_price', 'currency', 'is_clearance', 'is_featured',
    ];

    public function category(): BelongsTo
    {
        return $this->belongsTo(Category::class);
    }
}

Two ideas here:

  • $fillable lists the columns we allow to be mass-assigned. It is a security guard: only these fields can be set via Item::create([...]).
  • The category relationship says "an Item belongs to a Category." Once defined, you can write $item->category->name and Eloquent runs the join for you.

7.2 The Category model

class Category extends Model
{
    protected $fillable = ['name', 'slug', 'icon', 'heroimg'];

    public function items(): HasMany
    {
        return $this->hasMany(Item::class);
    }

    public function getHeroImageUrlAttribute(): string
    {
        if (!empty($this->heroimg) && file_exists(public_path('images/categories/' . $this->heroimg))) {
            return asset('images/categories/' . $this->heroimg);
        }
        return asset('images/categories/default.png');
    }
}
This is the clearest MVC lesson in the whole project. The View needs the URL of the category's hero image, and it needs to never show a broken image. Rather than putting that logic in the template (the View), it lives in the Model as an accessor — a method getHeroImageUrlAttribute() that Blade reads as $category->hero_image_url. The template just asks for the value; the Model decides where it comes from. Fat Model, thin View.

7.3 The User model

The User model extends Authenticatable (so it can act as a login user), declares $fillable for name/email/password, hides the password and remember token, and casts password as hashed — meaning Laravel automatically hashes it on save and verifies it on check.

8. The Database: Migrations and Schema

Instead of creating tables by hand in SQL, Laravel uses migrations — PHP files that describe changes to the schema. They are version control for your database. Each migration has an up() (apply) and a down() (undo). Run them with php artisan migrate.

8.1 The categories and items migration

Schema::create('categories', function (Blueprint $table) {
    $table->id();                 // integer primary key, auto-increment
    $table->string('name');
    $table->string('slug')->unique();
    $table->string('icon')->nullable();
    $table->string('heroimg')->nullable();
    $table->timestamps();
});

Schema::create('items', function (Blueprint $table) {
    $table->id();
    $table->foreignId('category_id')->constrained()->cascadeOnDelete();
    $table->string('name');
    $table->string('slug')->unique();
    $table->text('description')->nullable();
    $table->decimal('price', 10, 2)->default(0);
    $table->decimal('sale_price', 10, 2)->nullable();
    $table->string('currency', 3)->default('NGN');
    $table->boolean('is_clearance')->default(false);
    $table->boolean('is_featured')->default(false);
    $table->timestamps();
});

Key ideas:

  • $table->id() makes an auto-incrementing primary key.
  • slug->unique() tells the database to reject duplicate slugs — a rule the DB enforces, not the app.
  • foreignId('category_id')->constrained() creates a foreign key: every item's category must exist, and cascadeOnDelete means deleting a category deletes its items.
  • timestamps() adds created_at and updated_at automatically.
Real-life lesson: in this very project the unique index on items.slug was declared in the migration but never actually created in the live database — a kind of schema drift. Re-importing a spreadsheet silently produced duplicate rows. We had to add a later migration to create the missing index. The migration file is the source of truth for what the schema should be; the live database must be kept in sync with it.

9. The Controller Layer: Thin Coordinators

Controllers live in app/Http/Controllers/. Each public method is a controller action that handles one kind of request. The golden rule: controllers should be thin — validate input, ask the Model for data, pass it to a View. Heavy logic belongs in the Model.

9.1 HomeController

class HomeController extends Controller
{
    public function index()
    {
        $categories = Category::query()->orderBy('name')->get();
        $featuredItems = Item::query()->where('is_featured', 1)->orderByDesc('id')->limit(12)->get();
        $clearanceItems = Item::query()->where('is_clearance', 1)->orderByDesc('id')->limit(12)->get();

        $hero = [ 'title' => 'Welcome to Super Mart', /* ... */ ];

        return view('welcome', compact('categories', 'featuredItems', 'clearanceItems', 'hero'));
    }
}

It queries two lists of items, builds a hero banner array, and passes everything to the welcome view with compact() (a PHP helper that builds ['categories' => $categories, ...]). The controller does not know how the page looks; it only knows what data the page needs.

9.2 CategoryController

public function show(string $slug)
{
    $category = Category::query()->where('slug', $slug)->firstOrFail();
    $categories = Category::query()->orderBy('name')->get();
    $items = Item::query()->where('category_id', $category->id)->orderByDesc('id')->limit(36)->get();

    $hero = [ 'title' => $category->name, 'image' => $category->hero_image_url, /* ... */ ];

    return view('category', compact('category', 'categories', 'items', 'hero'));
}

firstOrFail() returns the category or a 404 if no category has that slug — a clean way to handle "page not found."

10. Routing: Connecting URLs to Controllers

Routes live in routes/web.php. A route maps a URL + method to a controller method, and gives it a name so the rest of the app can link to it without hard-coding the URL.

Route::get('/', [HomeController::class, 'index'])->name('home');
Route::get('/category/{slug}', [CategoryController::class, 'show'])->name('category.show');

Route::post('/cart/add/{item}', [CartController::class, 'add'])->name('cart.add');
Route::get('/cart', [CartController::class, 'index'])->name('cart.index');
Route::delete('/cart/remove/{item}', [CartController::class, 'remove'])->name('cart.remove');
Route::post('/cart/update', [CartController::class, 'update'])->name('cart.update');

Route::get('/admin', [ImportProductController::class, 'admin'])->name('admin');
Route::post('/admin', [ImportProductController::class, 'uploadExcel'])->name('admin.upload');

Things to notice:

  • {slug} and {item} are route parameters — whatever is in the URL gets passed as an argument.
  • The HTTP method matters: cart.add is POST (it changes data), cart.remove is DELETE. Using the right verb is part of RESTful design.
  • ->name('cart.add') lets the View say route('cart.add', $item) instead of writing /cart/add/5. If the URL changes later, the links still work.

11. Middleware: Gatekeepers Before the Controller

Middleware runs before the controller, inspecting or redirecting the request. Super Mart has two custom middleware in app/Http/Middleware/:

class EnsureAuthenticated
{
    public function handle(Request $request, Closure $next)
    {
        if (!$request->session()->has('user_id')) {
            return redirect()->route('account');
        }
        return $next($request);
    }
}
class EnsureGuest
{
    public function handle(Request $request, Closure $next)
    {
        if ($request->session()->has('user_id')) {
            return redirect()->route('account');
        }
        return $next($request);
    }
}

EnsureAuthenticated blocks logged-out users from protected pages; EnsureGuest does the opposite, keeping logged-in users away from the login/register pages. By doing this in middleware, no controller has to repeat "is the user logged in?" — the check lives in one place. This is the MVC philosophy extended: cross-cutting concerns belong outside the controller.

12. The View Layer: Blade Templates

Views live in resources/views/. Super Mart has welcome.blade.php (home), category.blade.php, allcategories.blade.php, cart.blade.php, admin.blade.php, account-info.blade.php, login.blade.php, plus auth/ and components/ directories.

A View only renders the variables it is given. For example, an item card on the home page:

@if(!empty($item->image))
    <img class="product-image" src="{{ asset('images/items/' . $item->image) }}" alt="{{ $item->name }}">
@endif

The View does not query the database — the controller already passed $item. It does not decide where the image lives — it just builds the URL from the filename the model stored. {{ ... }} escapes the output to prevent XSS attacks.

The discipline: if you ever find yourself writing a database query inside a Blade template, you are breaking MVC. Move that query to the controller (or better, a Model method) and pass the result in.

13. Feature: The Storefront

The home page (GET / → HomeController::index) shows all categories, twelve featured items, twelve clearance items, and a hero banner. The controller gathers them; the welcome view renders cards for each item with its image, name, and price. If an item has a sale_price, the cart logic later uses it; the storefront shows the regular price.

14. Feature: Category Pages

GET /category/{slug} → CategoryController::show. The slug is looked up; if it exists, the page shows the category's hero image (via the Model accessor we discussed) and up to 36 of its items, newest first. If no category matches, firstOrFail() returns a 404. This single route handles every category — /category/fruits, /category/meats, etc. — because of the {slug} parameter.

15. Feature: The Shopping Cart

The cart is interesting because it is stored in the session, not the database. The session is per-visitor temporary storage that lives between requests (usually in a cookie or a server file). The cart never hits the database until checkout — so it works even for anonymous visitors.

CartController keeps all session access behind two private helpers:

private function getCart(): array
{
    $cart = Session::get('cart', []);
    return is_array($cart) ? $cart : [];
}

private function setCart(array $cart): void
{
    Session::put('cart', $cart);
}

The add action:

public function add(Request $request, int $itemId)
{
    $quantity = max(1, (int) $request->input('quantity', 1));
    $item = Item::query()->findOrFail($itemId);

    $cart = $this->getCart();
    $key = (string) $item->id;

    if (!isset($cart[$key])) {
        $cart[$key] = [
            'item_id' => $item->id,
            'name'    => $item->name,
            'image'   => $item->image,
            'price'   => (float) ($item->sale_price ?? $item->price),
            'quantity'=> 0,
        ];
    }
    $cart[$key]['quantity'] += $quantity;

    $this->setCart($cart);
    return redirect()->route('cart.index')->with('success', 'Added to cart');
}

Notice: it uses the sale price if one exists, falling back to the regular price. The subtotal is computed in the index action — in the controller, not in the View:

foreach ($cart as $row) {
    $totals['subtotal'] += ((float) $row['price']) * ((int) $row['quantity']);
}

This is the MVC discipline again: presentation data (the subtotal) is prepared by the controller, so the template just prints {{ $totals['subtotal'] }}.

15.1 Why the verbs matter

Adding to the cart is a POST (it changes data); removing is DELETE; updating quantities is POST. A link (<a href>) can only do a GET, so the add-to-cart button must be a

with method="POST" and a @csrf field. This was an actual bug in the project's history: add-to-cart links used GET but the route was POST-only, so they failed. The fix was to make the Blade submit a POST form.

16. Feature: Authentication

Authentication is deliberately hand-rolled (rather than using Laravel's built-in Auth scaffolding) so the mechanics are visible. It has three pieces: register, login, logout, plus an account page.

16.1 Register

$validated = $request->validate([
    'name'     => ['required', 'string', 'max:255'],
    'email'    => ['required', 'email', 'max:255', 'unique:users,email'],
    'password' => ['required', 'string', 'min:8', 'confirmed'],
]);

$user = User::create([
    'name'     => $validated['name'],
    'email'    => $validated['email'],
    'password' => Hash::make($validated['password']),
]);

$request->session()->put('user_id', $user->id);
return redirect()->route('home')->with('success', 'Account created successfully');

validate both checks the rules and returns only the safe fields. Hash::make one-way-encrypts the password; the plain text is never stored. confirmed requires a matching password_confirmation field. After creating the user, we put user_id in the session — that is what "being logged in" means in this app.

16.2 Login

$user = User::query()->where('email', $validated['email'])->first();

if (!$user || !Hash::check($validated['password'], $user->password)) {
    return back()->withInput()->with('error', 'Invalid credentials');
}

$request->session()->put('user_id', $user->id);
$request->session()->put('user_name', $user->name);
$request->session()->put('user_email', $user->email);

Hash::check compares the submitted password against the stored hash — the stored password is never decrypted (it cannot be; hashing is one-way). On success, the session marks the user as logged in.

16.3 Logout

$request->session()->forget('user_id');
$request->session()->forget('user_name');
$request->session()->forget('user_email');

Logging out is simply removing those keys from the session. The "logged in" state is entirely a question of whether session('user_id') exists — which is exactly what the EnsureAuthenticated middleware checks.

17. Feature: The Admin Product Import

This is the most complex feature, and a great study of a real controller job: reading a spreadsheet, cleaning the data, resolving relationships, and saving — all safely.

The admin page (GET /admin) shows a form to upload an Excel file plus optional product images. The form posts to POST /admin → ImportProductController::uploadExcel. There is also a link to download a blank template spreadsheet from public/templates/.

17.1 Reading the spreadsheet

Using the maatwebsite/excel package, the controller reads the uploaded file into arrays:

$sheets = Excel::toArray([], $file);
$rows = $sheets[0];   // first worksheet

17.2 Detecting headers

Real spreadsheets may or may not have a header row. The code checks whether the first row contains words like "name", "slug", or "category":

$hasHeading = in_array('name', $firstLower, true)
            || in_array('category', $firstLower, true)
            || in_array('slug', $firstLower, true);
$startIndex = $hasHeading ? 1 : 0;

If headers exist, each row is keyed by its header name; otherwise a fixed column order is assumed. This makes the importer tolerant of both styles.

17.3 Resolving the category

The spreadsheet's category column can hold either a numeric id or a category name like "Meats". The controller handles both:

// If it's a number, look the category up by id
if (!empty($assoc['category_id']) && is_numeric($assoc['category_id'])) {
    $cat = Category::find((int) $assoc['category_id']);
    if ($cat) $categoryId = $cat->id;
}

// Otherwise, treat the value as a name and find-or-create the category
if (empty($categoryId)) {
    $catName = $assoc['category']
        ?? $assoc['category_name']
        ?? (is_string($assoc['category_id'] ?? null) ? $assoc['category_id'] : null)
        ?? 'uncategorized';
    $cat = Category::firstOrCreate(['slug' => Str::slug($catName)], ['name' => $catName]);
    $categoryId = $cat->id;
}

firstOrCreate either finds an existing category with that slug or creates one — so importing a product in a new category automatically creates the category.

17.4 Cleaning the data

Spreadsheets are messy. Prices may be written as "₦1,200.50" or "1,200". The importer normalises them:

$parseNumeric = function ($value) {
    if ($value === null || $value === '') return null;
    $v = str_replace([',', ' ', "\xc2\xa0", '$', '£', '€', '₦'], '', (string) $value);
    $v = preg_replace('/[^0-9.\-]/', '', $v);
    return is_numeric($v) ? (float) $v : null;
};

And boolean flags like "yes"/"true"/"1" become 1, anything else becomes 0:

$toBoolInt = function ($val) {
    if ($val === null || $val === '') return 0;
    return in_array(strtolower((string) $val), ['1','true','yes','y'], true) ? 1 : 0;
};

17.5 Inserting safely: transactions and firstOrCreate

The whole loop runs inside a database transaction:

DB::beginTransaction();
// ... loop inserting items ...
DB::commit();   // all good → save everything
// on any exception:
DB::rollBack(); // undo everything → no half-import

A transaction means either all rows insert, or none do — never a partial import. And each item uses firstOrCreate on the slug:

$item = Item::firstOrCreate(
    ['slug' => $slug],                 // match key
    [ /* the rest of the fields */ ]
);

This makes the import idempotent: re-importing the same sheet does not duplicate rows — existing slugs are skipped. (We will revisit this in the bugs section.)

17.6 Saving uploaded images

The controller also saves any uploaded product images to public/images/items/ using their original filenames:

$file->move($destination, $originalName);

The spreadsheet's image column stores the filename, and the storefront renders asset('images/items/' . $item->image). So for the image to display, the uploaded filename must match what the spreadsheet says.

18. Putting It All Together: One Request, End to End

Let us trace a real request: a visitor clicks "Meats" on the home page.

  1. Browser sends GET /category/meats to the server.
  2. Laravel's router matches it against Route::get('/category/{slug}', [CategoryController::class, 'show']) with $slug = 'meats'.
  3. Middleware runs (none restricts this public page).
  4. CategoryController::show('meats') runs.
  5. It asks the Model: Category::where('slug','meats')->firstOrFail(). Eloquent runs SELECT * FROM categories WHERE slug = 'meats' against the database.
  6. The database returns the Meats row; Eloquent turns it into a Category object.
  7. The controller fetches the items: Item::where('category_id', $category->id)...->get() → another SQL query → a collection of Item objects.
  8. The controller calls view('category', compact(...)), handing the data to the View.
  9. The Blade template renders HTML, using $category->hero_image_url (the Model accessor) and looping over $items.
  10. Laravel sends the finished HTML back as the response.
  11. The browser renders the page.

That is MVC in action: the request entered through the controller, the model supplied the data, the view shaped the output, and each layer stayed in its lane.

19. Bugs We Hit and How We Fixed Them

Real projects teach through their bugs. Here are the ones we hit, each one a lesson about MVC or the framework.

19.1 Add-to-cart used the wrong HTTP method

Symptom: clicking "Add to cart" failed.

Cause: the Blade used an <a href> link (a GET) but the route was Route::post('/cart/add/{item}', ...). A GET request cannot match a POST-only route.

Fix: change the link to a <form method="POST"> with @csrf, posting to route('cart.add', $item).

Lesson: HTTP methods are not decorative — they are part of the route's identity.

19.2 The categories table had no primary key

Symptom: importing a spreadsheet failed with NOT NULL constraint failed: categories.id.

Cause: the live categories table had been created with id as a NOT NULL column that was neither a primary key nor auto-increment. So any Category::create() failed — and the importer tried to create an "uncategorized" category whenever it could not match the sheet's category, which crashed the whole import.

Fix: a migration that recreates categories with a proper $table->id(), preserving the existing rows and their ids.

Lesson: the migration is the source of truth; the live DB can drift from it. Verify the actual schema with PRAGMA table_info, not just by reading the migration file.

19.3 The importer read the wrong column

Symptom: the sheet had a category_id column holding the name "Meats", but the importer looked for a column named category (which did not exist), defaulted to "uncategorized", and crashed.

Cause: a mismatch between the spreadsheet's column names and the importer's expected keys.

Fix: add a fallback so that when category_id holds a string, it is treated as the category name.

Lesson: real-world data does not always match your assumptions. Build importers that tolerate the shapes you will actually receive.

19.4 Re-importing duplicated items

Symptom: uploading the same spreadsheet twice produced exact duplicate rows.

Cause: the items.slug unique index declared in the migration was never created in the live database, so nothing stopped the duplicate. And Item::create() always inserted.

Fix: two changes — (a) a migration to create the missing items_slug_unique index, and (b) change Item::create() to Item::firstOrCreate(['slug' => $slug], [...]) so existing slugs are skipped.

Lesson: a unique constraint is a database rule — but the application should still behave well when the constraint would fire. firstOrCreate makes the operation idempotent.

19.5 A broken image from a typo

Symptom: an imported item's image did not display, even though the image file was in the correct folder.

Cause: the spreadsheet said raw-chiken.jpg (a typo) but the uploaded file was named raw-chicken.jpg. The importer stored the spreadsheet's value, and the storefront rendered images/items/raw-chiken.jpg — a file that did not exist.

Fix: correct the spreadsheet (or the database row) so the filename matches the uploaded file.

Lesson: when two sources of truth must agree (the filename and the spreadsheet's image cell), a mismatch produces a silent failure — a broken image, not an error. Validate that they match.

20. What This Project Taught Us About MVC

  • The Model is not just storage. Accessors like hero_image_url and relationships like items() put data logic where it belongs — on the thing that owns the data.
  • The Controller should be boring. Validate, fetch, pass to the view. If a controller method is long, logic is probably leaking out of the Model.
  • The View should be dumb. It renders what it is given. No queries, no decisions about where data comes from.
  • The database enforces rules the app should not have to repeat. Unique constraints, foreign keys, and not-null columns catch bugs at the storage layer.
  • Middleware handles cross-cutting concerns. Auth checks, CSRF, guest-gating — none of these belong in every controller.
  • Names matter. Named routes (route('cart.add')) decouple URLs from links. Slugs make URLs readable and stable.
  • Transactions keep data consistent. An import either fully succeeds or fully rolls back — never a half-written state.
  • Idempotence is a virtue. An operation you can run twice safely (firstOrCreate) is an operation you can trust.

By the end, the layers of Super Mart are:

routes/web.php — URL → controller mapping │ Middleware — auth / guest gates │ Controllers (app/Http) — validate, fetch, hand off │ Models (app/Models) — data, relationships, accessors │ Eloquent → SQLite — persistence │ Views (resources/views) — render HTML │ Response → Browser
